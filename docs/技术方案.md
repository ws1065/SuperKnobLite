# SuperKnobLite 功能扩展技术方案

> 在原厂固件（2023-01 基线）之上，新增**串口远程电机控制**、**可切换触觉模式**、**位置感知上报**、**屏幕诊断**能力，并配套一个纯前端串口控制台。
>
> 编写日期：2026-10-01　| 硬件：ESP32-PICO-D4 + DRV8313 + AS5600 + 7 极对无刷云台电机

---

## 一、背景与目标

原厂固件的串口协议仅支持单向注入 `{"cpu":x,"memory":y}`（驱动屏幕上的「电脑监测」页），其余能力（电机手感、页面切换、灯光）均无串口入口。SimpleFOC 的 commander 接口虽已在源码中定义 `T<angle>` 指令，但被 `#ifdef ENABLE_SIMPLEFOC_STUDIO` 编译期禁用（`main.h` 中该宏处于注释状态），故原厂固件**不具备任何远程电机控制能力**。

扩展目标：

| 目标 | 落地方式 |
|---|---|
| 远程控制电机按指定方式运动 | 扩展串口协议，新增角度环接管 |
| 提供多种可切换的触觉手感 | 重构 FOC 力矩算法为多模式触觉引擎 |
| PC 侧实时感知旋钮位置/角度 | 固件周期上报，页面解缠绕求累计圈数 |
| 安全可控的转速调节 | 速度闭环 + 多重限幅 |
| 屏幕可用性判定 | ST7735 寄存器回读 + 绕过 LVGL 的纯色刷屏 |

## 二、串口协议扩展设计

### 2.1 向后兼容策略

原协议 `{"cpu":x,"memory":y}` 保持**完全不变**，新指令通过 **`t` 字段（type discriminator）**区分：

```cpp
DeserializationError error = deserializeJson(doc, received_chars);
if (error) { /* 原厂错误处理 */ }

if (doc["t"].is<const char*>())      // 有 t → 新协议
    handle_extended_command();
else                                  // 无 t → 原厂 cpu/memory 逻辑
    { PC_MONITOR.monitor_cpu = doc["cpu"]; /* 原厂回显 */ }
```

**为什么不用 `"t":1` 数字类型**：字符串可读性更好，且便于未来扩展 `"haptic"`、`"motor"`、`"sys"` 等多个命名空间，避免顶层字段冲突。

### 2.2 报文规范

- **帧格式**：一行一条 JSON，`\n` 结尾（固件原有解析器按 `\n` 切分）
- **请求**：`{"t":"<类别>","cmd":"<指令>",...参数}`
- **应答**：每条指令固定回一条 `{"t":"ack","cmd":"<指令>","ok":true|false}`
- **主动上报**：`{"t":"pos",...}`（位置）、`{"t":"status",...}`（状态查询）

**关键约束**：设备向 PC 发出的**纯数字行**（`16.70`）是 PC 心跳回显的匹配依据，任何新增输出都**不得**是裸数字行，必须是 JSON 对象，避免打乱 PC 侧的 FIFO 匹配队列。

### 2.3 指令总表

| 类别 | 指令 | 参数 | 说明 |
|---|---|---|---|
| `haptic` | `set` | `mode`: detent/spring/viscous/oneway/endstop/free | 切换触觉模式 |
| `haptic` | `set` | `mode:endstop` + `range` | 限位半宽（弧度） |
| `haptic` | `velservo` | `enable`, `speed`(可负=反转), `max` | 转速伺服开关与调速 |
| `haptic` | `report` | `enable`, `interval`(ms) | 位置感知上报开关 |
| `motor` | `hold/rotate/sweep/step/release` | `angle/speed/dir/range/pos` | 角度环远程接管 |
| `sys` | `ping/status` | — | 连通性与状态查询 |
| `sys` | `display_test` | `mode`: start/stop | 纯色刷屏自检 |
| `sys` | `display_diag` | — | ST7735 寄存器回读 |

## 三、固件架构改造

### 3.1 FOC 控制环的优先级设计

原 `Task_foc`（Core1，优先级 2，1kHz）是唯一的电机控制任务，其循环体原本只有「detent 力矩算法」一条路径。扩展后按**优先级抢占**组织为四级，命中即 `continue`：

```
for(;;) {
    motor.loopFOC();
    [位置感知上报]                       ← 每周期执行，不影响控制
    xQueueReceive(LVGL→电机 消息)        ← 原厂页面切换/触摸事件
    if (g_remote_mode != REMOTE_OFF)  { 角度环接管;  continue; }   ① 远程接管（最高）
    if (g_vel_servo_on)              { 速度闭环;    continue; }   ② 转速伺服
    if (g_haptic_mode != DETENT)     { 触觉力矩;    continue; }   ③ 多模式触觉
    /* ④ 原厂 detent 力矩算法（含防飞车保护） */
}
```

**设计要点**：采用「分支 + continue」而非「状态机 + switch」，因为各模式对控制环的接管是互斥且临时的，回落到 detent 时无需重建状态；且任一高级模式退出后，detent 算法的 `current_detent_center` 等局部状态保持不变，退出瞬间不会产生力矩跳变。

### 3.2 多模式触觉引擎

所有模式统一在**力矩控制**（`MotionControlType::torque`）下计算 `torque`，再 `motor.move(torque)`。以进入模式时捕获的 `center = motor.shaft_angle` 为零点，`delta = shaft_angle - center`：

| 模式 | 力矩公式 | 系数 | 手感机理 |
|---|---|---|---|
| 弹簧回中 | `-2.5 × delta` | K=2.5 | 偏离越远回弹力越大，线性回中 |
| 粘滞搅拌 | `-0.15 × velocity` | K=0.15 | 阻尼只与转速有关，静止时无力矩，停即停 |
| 单向棘轮 | 正转 `-0.02v`；反转 `+2.0×(-v)` | 阈值 -0.05 | 非对称阻力，单向棘轮扳手感 |
| 离心限位 | 范围内 `-0.1×delta`；超出 `-8×(|delta|-range)×sign` | range 默认 3.0 | 软回中 + 硬限位墙 |
| 自由飞轮 | `-0.004 × velocity` | K=0.004 | 极低粘性阻尼，时间常数 1/K≈250s |

**安全约束**：所有模式力矩统一 `CLAMP(±10)`，粘滞/棘轮/限位各自额外收紧；**防飞车保护 `|velocity| > 60 rad/s → move(0)` 在所有模式下保留**。

### 3.3 转速伺服（速度闭环）

与触觉模式的力矩控制不同，伺服采用 `MotionControlType::velocity` 速度闭环，由 `PID_velocity`（P=0.6, I=1.5, D=0）调节电压：

```cpp
motor.controller = MotionControlType::velocity;
motor.PID_velocity.P = 0.6f; motor.PID_velocity.I = 1.5f;
motor.voltage_limit = 8.0f;                       // ① 电压限幅，防大电流
float t = CLAMP(g_servo_target, -g_servo_max, g_servo_max);   // ② 目标钳制
if (g_vel_servo_max 越界) g_vel_servo_max = CLAMP(..., 1.0f, 20.0f);  // ③ max 自身钳制
motor.move(t);
if (fabsf(motor.shaft_velocity) > 60.0f) motor.move(0);          // ④ 防飞车
```

**四重安全设计**：max 在 `vel_servo_enable()` 入口与 `Task_foc` 每周期**双重钳制**（防止全局变量被脏数据污染）；目标值每周期重新钳制；叠加电压限幅；保留原有防飞车。实测请求 50 rad/s 被正确钳到 `servo_target = 20.00`。

关闭伺服时恢复力矩控制器参数并 `haptic_set_mode(HAPTIC_DETENT, 0)`，交还正常触觉。

### 3.4 跨任务并发安全

串口命令在 Arduino `loop()` 任务（优先级 1）写入共享状态，`Task_foc`（优先级 2）读取，中间存在抢占窗口。采用**参数先写、模式标志后写**的顺序（volatile 变量）：

```cpp
void motor_remote_set(...) {
    g_remote_p1 = p1; g_remote_p2 = p2; g_remote_p3 = p3;
    g_remote_mode = mode;      // 最后写，作为「参数就绪」标志
}
```

这样 `Task_foc` 读到新 mode 时，其参数必然已经完整写入。

### 3.5 位置感知上报

`Task_foc` 中按 `millis()` 限频（默认 50ms / 20Hz）上报 JSON。上报频段的带宽占用约 800 B/s，远小于 115200 波特率（11.5 KB/s）承载能力，不会影响命令响应。

## 四、屏幕诊断方案

针对「背光亮但全黑」问题，设计两级判定：

**第一级 —— 电气层判定**：ST7735 的 `0xDA/0xDB/0xDC` 寄存器可通过 MISO 回读（`tft.readcommand8()`）。全为 `0x00`/`0xFF` 表明面板未驱动 MISO（浮空高电平特征）。

**第二级 —— 渲染层隔离**：设置 `g_disp_test_active` 标志使 `my_disp_flush()` 直接返回（**必须仍调用 `lv_disp_flush_ready()`，否则 LVGL 死锁**），另起 FreeRTOS 任务直接 `tft.fillScreen()` 循环刷红/绿/蓝/白，**完全绕过 LVGL**。若能看到颜色则面板与 SPI 正常，问题在 LVGL 渲染层；仍全黑则为硬件故障。

**实测结论**：寄存器全读 `0xFF` + 纯色刷屏无任何显示 → 判定面板/排线硬件损坏。

## 五、控制台前端设计

### 5.1 技术选型：Web Serial API

选 Web Serial API 而非原生应用/服务端代理，理由：

- **零安装**：纯静态单文件 HTML，双击即可用，无需 Python 环境或打包；
- **直通串口**：数据不经中间层，RTT 测量真实（心跳验证 100/100 包，成功率 100%，RTT 均值 62ms / P95 108ms）；
- **生态成熟**：Chrome/Edge 原生支持（Safari 不支持，需在页面内提示）。

代价是需要浏览器授权，且无法采集系统级 CPU —— 后者用独立的 Node 采集服务（`tools/knob_server.mjs`）解决。

### 5.2 可靠性测试的内容校验

心跳不只检查「有没有回包」，而是**逐包校验回显数值与发送值一致**（容差 ±0.05），从而能发现链路上的比特级错误。

### 5.3 角度解缠绕

AS5600 经 SimpleFOC 换算的 `shaft_angle` 在 0~2π 圈内回绕，直接 `angle/2π` 只能得到圈内小数。页面侧维护累计角：

```js
let dlt = raw - posLastRaw;
if (dlt >  Math.PI) dlt -= 2*Math.PI;   // 跨 +2π 边界
if (dlt < -Math.PI) dlt += 2*Math.PI;   // 跨 -2π 边界
posUnwrapped += dlt;
```

实测验证：正向 5.9→6.2→0.1 rad 正确累加为 +0.483 rad（而非错误跳变），累计圈数单调递增。

### 5.4 屏幕功能折叠

考虑到屏幕可能损坏（部分用户的设备无屏），所有屏幕相关内容（实时资源监控、屏幕诊断）收进 `<details>` 折叠区，默认收起，避免影响电机等主功能的可用性。

## 六、踩坑记录（重要）

### 6.1 CH343 CDC 链路的方向性丢包 ★

**现象**：`esptool` 同步、擦除等小命令正常，但 stub 上传（~8KB）与 flash 数据写入必然失败，报 `0107 Checksum error` / `0105 invalid message format`。降低波特率（115200/57600）无效。

**定位**：256 KB 回读逐字节校验通过（仅 2 字节差异，实为不同固件构建的头部差异）→ 证明**接收方向完好**；发送方向小包成功、大包失败 → 定位为 **PC→设备方向的大批量突发写入溢出 CH343 缓冲**。

**解决**：分片节流写入，将有效速率压到 UART 承载率以下：

```python
SLICE, DELAY = 64, 0.006    # ≈5.5 KB/s
def paced_write(self, data, ...):
    for i in range(0, len(data), SLICE):
        raw_write(self, data[i:i+SLICE]); self.flush(); time.sleep(DELAY)
```

封装为 `tools/paced_esptool.py`，monkeypatch `serial.Serial.write` 后调用 esptool 本体，**保留其全部协议正确性逻辑**，只改写入节奏。2 MB 固件约 4.5 分钟，哈希校验通过。

### 6.2 esptool `--no-stub` 必要性

CDC 模式下 stub 下载器上传必然校验失败，必须使用 `--no-stub` 走 ROM loader。

### 6.3 pyserial 复位时序的中间态陷阱

用 `setDTR(True)` + `setRTS(False)` 依次设置进入下载模式时，两次独立 ioctl 之间的中间态 (DTR=1, RTS=1) 会**提前释放 EN**，导致芯片走正常 SPI 启动而非进入下载模式。esptool 用 `ioctl(TIOCMSET)` **原子设置双引脚**规避此问题（`esp_pylib.serial_reset.unix_tight_bootloader_reset`）。

### 6.4 打包固件 bin 与仓库源码不同源 ★

`zeasy_upload_bin/firmware.bin`（2022-09 打包）与两个工程的 `.pio` 构建产物 **MD5 均不同**。烧录打包 bin 后设备虽能正常启动、logo/电机/LVGL 日志齐全，但**对串口输入零响应**（洪泛 11500 行亦无回显）。改用与源码同源的 `.pio` 构建后协议回显恢复正常（100/100 包通过）。

**教训**：预编译 bin 不代表当前源码的行为，必须以本地构建产物为准。

### 6.5 自检永久挂起的 Promise 缺陷

页面心跳 `sendPing()` 返回 Promise，但成功回显路径中只清理了超时定时器、**未兑现 Promise**，导致 `await` 永久挂起（超时已被清除，无法自救），自检永远停在「运行中」。修复：成功路径调用 `p.resolve(true)`。修复后单元测试验证：回显到达时 0ms 返回。

### 6.6 Apple Silicon 工具链

`espressif32@4.1.0`（2021 年平台）在 Apple Silicon 上**实测可正常编译**（全量 79s / 增量 6.6s），无需升级到 6.x，规避了 AGENTS.md 中担心的兼容问题。

## 九、遗留事项与后续方向

1. **屏幕硬件**：需更换屏幕模组或重新压接排线；换屏后可用页面「屏幕诊断」卡片复验。
2. **原厂固件解析缺陷**：`main.cpp` 解析失败后不清空接收缓冲导致永久失步，建议在后续版本修复为 `received_chars = ""`。
3. **触觉参数标定**：各模式力矩系数为工程经验初值，可依实际手感继续调优（建议提供页面参数调节）。
4. **协议扩展方向**：页面切换、灯光颜色、BLE 键值映射等仍无串口入口，可按同一 `t/cmd` 规范继续扩展。
5. **OTA**：当前固件 2.09 MB，接近 3 MB 分区上限；如需 OTA 须裁剪至 <1.9 MB（双分区）。
